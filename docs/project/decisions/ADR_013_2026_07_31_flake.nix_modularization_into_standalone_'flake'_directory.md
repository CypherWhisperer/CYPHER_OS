# ADR_013_2026_07_31: `flake.nix` Modularization into `flake/`

**Date:** 2026-07-31 
**Status:** Accepted
**Deciders:** CypherWhisperer

---

## Context

`flake.nix` previously held its entire `outputs` function inline: the shared `pkgs` instantiation, the full `nixosConfigurations.cypher-nixos` definition *(system config import, Home Manager NixOS-module wiring, per-user HM config),* and the full `homeConfigurations."cypher-whisperer@cypher-nixos"` definition, all in one `let ... in { ... }` block. 

This was becoming harder to navigate as the file accumulated content, and stood in visible contrast to the rest of the repository, where `modules/` is already deeply subdivided by domain *(`modules/apps/*`, `modules/de/*`, `modules/devops/*`, etc.)* — `flake.nix` was the one major piece of the configuration not following that pattern. 

Implementing [ADR_012_2026_07_31](ADR_012_2026_07_31_overlays_and_nixpkgs.config_single_source_of_truth.md) *(extracting overlays/`nixpkgs.config` into their own file)* made this the natural moment to extract the rest at the same time, rather than adding one new split file to an otherwise-monolithic `outputs` function.

## Decision

`flake.nix`'s `outputs` function is reduced to the `inputs` destructuring plus `import ./flake { inherit inputs; }`.

Everything it previously did is split across `flake/default.nix` (composition point — builds shared `pkgs`, calls the other files, assembles the final outputs attrset), `flake/nixpkgs-config.nix` (per ADR_012), `flake/hosts.nix` (`nixosConfigurations`), `flake/home-configurations.nix` (`homeConfigurations`), and `flake/devshells.nix` (`devShells.<system>`, currently an empty stub).

`flake-parts` was considered and explicitly deferred — see Alternatives.

## Reasoning

This is a structural refactor, not a behavioral one (aside from the ADR_012 changes bundled into the same pass):

- the same attribute paths *(`nixosConfigurations.cypher-nixos`, `homeConfigurations."cypher-whisperer@cypher-nixos"`)* resolve to files organized by concern instead of by position in one large function body, mirroring the domain-split convention already established across `modules/`.
  
- Splitting by output type *(hosts vs. home-configurations vs. devshells vs. shared config)* rather than, say, splitting `nixosConfigurations` itself into per-host files now was chosen because `cypher-nixos` is currently the only host — a per-host split *(`flake/hosts/nixos/default.nix`, etc.)* is deferred until a second host is actually being added, per the phased plan below, to avoid introducing directory structure for hosts that don't exist yet.

## Alternatives Considered

### Adopt `flake-parts` now

`flake-parts` restructures flake outputs as composable modules *(with a `perSystem` scope that removes the need to repeat `system = "x86_64-linux"` at every call site)* rather than a hand-rolled attrset, and is the more idiomatic tool for this kind of split as of current Nix community convention. 

Rejected for now: 
- it adds a flake input to pin and one more layer between a config error and its actual source *(debugging goes through `flake-parts`' own module evaluation in addition to CypherOS's),* and its main structural benefit — clean multi-architecture/multi-system composition — isn't yet needed with a single `x86_64-linux` host. The plain-file `flake/` split captures most of the organizational win.
- This is not a one-way door:
    - adopting `flake-parts` later means converting file boundaries into module boundaries, not restructuring the underlying host/HM config.

### Leave `flake.nix` as one file, only extract `nixpkgs-config.nix` for ADR_012

Would satisfy ADR_012 alone with a smaller diff. Rejected because it leaves `flake.nix` as a monolith with one new import bolted on, rather than resolving the actual complaint *(a large single-file `outputs` function inconsistent with the rest of the repo's module-per-concern convention)* — the marginal cost of splitting the other two output types at the same time was low relative to doing it as a separate, later pass.

## Consequences

**Positive:**

- `flake.nix` itself is now a thin, stable entry point — future changes to hosts, HM config, or devshells touch `flake/*.nix` files directly and rarely require editing `flake.nix` at all
  
- Matches the domain-split convention already used throughout `modules/`, reducing the "this one file works differently" surprise for future navigation
  
- `flake/devshells.nix` gives future devshell work (nixamp and beyond) an obvious, already-scaffolded home instead of accumulating inline in `outputs`
  
- Directly enables per-host extraction later *(`flake/hosts.nix` → `import ./hosts/nixos { ... }` per prior discussion)* without further restructuring of the composition layer

**Negative / Trade-offs:**

- One more level of file navigation to trace a given `nixosConfigurations`/`homeConfigurations` definition back to its source, versus previously finding everything in `flake.nix` directly
  
- `flake/default.nix` is now a load-bearing composition point — *an error there is less immediately traceable to "which output" than when everything was inline in one function body*

**Neutral / Operational:**

- No change to `--flake .#<attr>` invocation syntax anywhere — this refactor is invisible to every command already in use *(`nixos-rebuild switch --flake .#cypher-nixos`, `home-manager switch --flake .#cypher_whisperer@cypher-nixos`, `nix flake check`)*
  
- `flake/hosts/nixos/default.nix`-style per-host extraction remains a deferred, opt-in next step — not undertaken in this pass since `cypher-nixos` is still the only host
